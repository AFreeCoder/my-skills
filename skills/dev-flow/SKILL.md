# Dev Flow

## 定位与边界

本 skill 固化两条 issue 驱动的路径：

1. **小任务直通**（明确 bug、小功能优化）：全自动走完"创建 issue → 问题分析 → 实施 → 测试 → 评审 → 合入发布 → 回填关闭"，仅在熔断时找人。
2. **阶段式留档**（大需求的各阶段，含纯讨论、调研）：需求分析、方案设计、任务拆分与计划编写等阶段各自独立 issue。这些阶段人深度参与，本 skill 的核心义务是把沟通结论及时同步到 issue。

范围外的任务（探索性重构、跨仓库变更、无法归入以上两类的工作）不适用本流程，不要强行套用。**路径拿不准时一律按阶段式处理**，代价只是多一次确认。

## 共享协议（issue 管理）

issue 操作（创建、评论、打 label、关闭等）用简短意图描述即可，具体通过 `gh` CLI 还是宿主环境的 GitHub 类 skill 执行，由模型按当前环境自行选择。

### 创建或续用 issue

- **先判断是否已有承载本次工作的 issue**：评审、补充讨论、迭代已有结论等针对既有产物的工作，一律续用原 issue，不新建。续用时（含用户指定续用），**写入前先完整读取其正文与全部评论**，增量追加，不重复、不与已有结论冲突。
- 新建时：标题概括问题或需求；打 label、分配给当前账号。
- label 只用仓库已有的默认 label，不新建：`bug`（缺陷）、`enhancement`（需求）、`question`（讨论、调研）。分类模糊时按最接近的打，后续可改——真正影响行为的是路径判断，不是 label。

### 同步（收敛快照，追加式）

issue 是**档案，不是工作台**：不逐句转录讨论，每次写回一段自包含的**收敛快照**。

- **快照写什么**：当前结论；关键取舍理由（含被否决的方案及原因）；仍待定的问题。有沉淀价值的过程信息通过前两项保留，逐条往返不进 issue。
- **时机**：议题收敛出结论或做出决策时立即写回，不攒批；实施完成、发布之后各同步一次；会话结束前兜底检查有无漏写。事后有新想法或补充，随时追加新评论，同样按快照写——上一条快照的"待定问题"就是它的挂载点。
- **版本**：只追加、不改写已有内容。结论被推翻时，新评论写明新结论与变更原因——追加式的评论流本身就是版本历史。

### AI 生成标识

AI 写回 issue 的所有内容（正文、评论），开头加声明前缀并标明当前宿主 Agent，与用户本人发言区分：

```
> *本内容由 AI 生成（Claude Code）*
```

宿主为 Codex 时写 `（Codex）`，其余环境同理。

### 关闭、重开与拆分

- 关闭、重新打开、拆分 issue 由用户决定；模型可提议（说明理由），不得自行执行。唯一例外：小任务直通发布验证通过后自动关闭。

## 小任务直通

1. **创建 issue**：按共享协议执行。
2. **问题分析**：定位根因、给出修复方向，写入 issue。启动子 Agent 对分析做独立评审，按意见迭代，**最多 3 轮**。根因显而易见的琐碎修复（typo、文案级）可省略本段评审，在 issue 中说明。
3. **实施**：按全局规范在独立 feature 分支和 worktree 中进行；遵守全局基线约束（不过度设计、不过度测试、关注主线）。
4. **实施评审**：启动子 Agent 对改动做独立评审，按意见迭代，**最多 3 轮**。
5. **测试**：运行与改动主线相关的测试，不扩大范围。
6. **发布**：评审与测试通过后合入，调用 push-deploy skill 发布。
7. **回填与关闭**：实施摘要、关联 commit、部署结果写回 issue；关闭前按全局文档规范（`~/.codex/docs-convention.md`）检查是否需更新常青文档；发布验证通过后关闭。有遗留事项则不关闭，写明待确认内容等用户处理。

### 熔断条件

命中任一条，立即停止自动流程，把当前状态同步到 issue，等用户确认：

- 任一段评审迭代 3 轮仍未通过
- 测试失败且无法通过琐碎修复解决
- 实施中发现改动规模明显超出预期
- 涉及数据迁移、配置变更或依赖升级

## 阶段式留档（大需求与纯讨论）

一个大需求不塞进一个 issue。**一个 issue 只承载一个阶段**，标题标明阶段（如 `[需求]`、`[方案]`、`[计划]`、`[实施]`），正文开头引用上游 issue 编号，形成可追溯的链：

- **[需求]**：只讨论需求本身——背景、目标、边界与结论。纯讨论、调研类工作即一个独立的需求或调研 issue，可以不往后走。
- **[方案]**：方案讨论与设计结论。**方案经用户确认后才进入实施**。
- **[计划]**：任务拆分与实施计划。
- **[实施]**：实施过程与发布记录。规模大时可按计划拆成多个批次 issue（模型提议、用户确认）。实施遵守全局分支规范与基线约束；评审深度按实际情况定，不套用固定 3 轮；发布经用户确认后执行。

阶段结论的沉淀按全局文档规范（`~/.codex/docs-convention.md`）执行：`[需求]`、`[方案]` 的结论经用户确认后分别沉淀到 `docs/requirements/`、`docs/design/` 的对应 feature 目录，下一阶段以沉淀文档为权威输入，issue 链只作过程追溯；`[计划]`、`[实施]` 属执行安排与记录，只留 issue、不沉淀。

对阶段产物的评审不构成新阶段：评审结论按收敛快照追加到被评审的阶段 issue，不另开 issue。评审推翻已沉淀文档的结论时，经用户确认后原地更新对应文档。

相邻阶段规模小时可合并进同一 issue——模型提议、用户确认。各阶段 issue 的关闭均由用户决定。

## 发布边界

发布一律调用 push-deploy skill 执行，并把结果回填 issue；本 skill 不含任何部署逻辑，部署细节、回滚、CI 监控以 push-deploy 为准。

## 项目覆盖

本 skill 的默认约定（GitHub 平台、分配当前账号、默认 label 集）不设配置项；个别项目约定不同时，以该项目 CLAUDE.md / AGENTS.md 中的声明覆盖。
