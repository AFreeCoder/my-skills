# 测试范围规划指引（阶段 0）

本文档是 `multi-agent-test-iteration` skill 第 0 阶段的执行指引。阶段 0 的唯一产出是**一份经人类确认的测试矩阵**，它决定了后续阶段的测试边界与深度。在进入阶段 1（写测试）之前，必须严格完成本文档描述的所有步骤。本文档同时被**产矩阵子 agent**（Author 角色）和**范围对抗子 agent**（Reviewer 角色）引用，二者分别从不同视角共同完成矩阵的产出与审核。

---

## 目标

在动手写任何测试代码之前，先产出一份**经人类确认的测试矩阵**（测试目标 × 测试层级），明确界定"测什么、测到什么程度"。

**不局限于 DESIGN.md**：设计文档只描述了系统"应当如何工作"，但大量应测的点——边界条件、异常分支、错误处理路径、并发/竞态、集成边界、安全面（鉴权/越权/注入）——在设计文档里往往没有显式写出来。Orchestrator 与 Author 子 agent 必须读真实实现代码，将这些**超出设计的补充项**识别出来并补入矩阵，而不是仅凭设计文档推导测试范围。

本阶段结束的验收条件：

- 测试矩阵文件 `test-matrix.md` 已落地于工作目录。
- 范围对抗子 agent 的评审 JSON（`scope-review-round-1.json`，或多轮后的最终版本）不含未解决的 `coverage-gap` 类 blocker/major。
- 矩阵已经过人类检查点①的确认，人类已签字冻结范围。
- 隔离分支/worktree 已建立，不在主干上直接测试。

---

## 调研输入

在启动产矩阵子 agent 之前，Orchestrator **必须亲自先读完以下输入**，并将关键摘要写入 prompt 传给子 agent，不能依赖子 agent 自行去找文件。

### 必读文档

1. **`DESIGN.md`（冻结版）**
   - 读设计目标、接口定义、数据模型、关键流程、已知限制。
   - 提取所有"功能场景"清单，作为测试矩阵行的初始来源。
   - 注意哪些内容是明确"本期不做"的——这些边界本身也是测试关注点（确保系统在边界外正确拒绝）。

2. **实现代码**（以 `文件:行` 指针形式传给子 agent）
   - 从入口文件开始，按调用链逐层阅读，直到覆盖所有面向外部的接口实现。
   - 重点关注：条件分支（`if/else/switch`）、错误抛出（`throw/return error/reject`）、并发操作（锁/队列/并行调用）、权限检查（`auth/permission/role`）、外部调用（数据库/缓存/第三方 API）。
   - 将找到的**设计文档未提及的逻辑路径**逐条记录，格式为 `文件:行 — 描述`，这些都是「超出设计的补充项」的候选。
   - 示例指针格式：`src/api/user.ts:42 — 注册时若邮箱已存在抛 409，DESIGN 未提`。

3. **`dev-log`（若存在）**
   - 读 dev log 中"已写单测"的记录，整理出一份"已覆盖的单元测试清单"。
   - 作用：在测试矩阵的单元层级列中，对已覆盖项标注"已由 dev-log 覆盖"，仅补强其边界/异常，不重复编写相同场景的正路径单测。
   - 如果 dev-log 不存在，则在矩阵注脚中标注"无 dev-log，单元层级全量规划"。

### 调研输出格式

完成调研后，Orchestrator 将以下内容落地为文件 `scope-input-summary.md`，供 Author 子 agent 和 Reviewer 子 agent 读取：

```
# 调研摘要

## 功能场景清单（来自 DESIGN）
- <场景名>: <一句话描述>
- ...

## 超出设计的补充项候选
- <文件:行> — <描述>
- ...

## dev-log 已覆盖的单测
- <测试名/函数名>: <覆盖场景>
- ...（若无则写"无"）
```

## 产测试矩阵

Orchestrator 委派**产矩阵子 agent**（Author 角色，使用 `general-purpose` 类型，全新上下文）产出 `test-matrix.md`。子 agent 的 prompt 必须显式传入以下内容：

- `scope-input-summary.md` 的绝对路径（调研摘要）。
- `assets/test-matrix-template.md` 的绝对路径（模板）。
- 本节对矩阵结构的完整要求（见下文）。

### 矩阵结构要求

矩阵以 Markdown 表格呈现，**行 = 测试目标/功能场景**，**列 = 测试层级**。行按功能聚类，不按文件或模块分割。列固定为四个层级：单元（Unit）、集成（Integration）、功能（Functional）、UI/E2E。

每个单元格填写：**是否适用**（"适用"/"不适用"）+ **验收点**（1-2 句话描述通过该层级测试的最低要求）。

示例行（用户注册流程）：

| 测试目标 | 单元 | 集成 | 功能 | UI/E2E |
|---|---|---|---|---|
| 用户注册流程 | 适用 — 邮箱格式校验逻辑返回正确结果 | 适用 — 注册接口写入数据库且返回 201 | 适用 — 完整注册→登录→访问受保护资源链路通过 | 适用 — 注册表单提交后页面跳转到欢迎页 |

### 必须包含「超出设计的补充项」列

在标准四列之后，矩阵每行必须额外添加一列**「超出设计的补充项」**。该列的作用是强迫 Author 子 agent 将从实现代码中读到的、DESIGN 未明确写出的测试点显式记录下来，防止其被遗忘或忽略。

该列填写格式：

- 若存在补充项：逐条列出，格式为 `<文件:行> — <测试要点>`，例如 `src/api/user.ts:58 — 并发注册同邮箱的幂等性（数据库唯一约束触发时返回 409 而非 500）`。
- 若无补充项：填写"无"，但 Reviewer 子 agent 将对此持怀疑态度并重点审查。

补充项的典型来源（Author 子 agent 必须逐类检查）：

- **边界值**：输入参数的最大/最小值、空字符串、null/undefined、类型不符。
- **异常分支**：代码中存在但 DESIGN 未描述的错误返回路径（如数据库连接失败、外部 API 超时）。
- **错误处理**：`catch` 块的行为是否符合预期，错误消息是否泄露内部信息。
- **并发/竞态**：两个请求同时修改同一条记录时的行为。
- **集成点**：与数据库、缓存、消息队列、第三方服务的真实交互（不能只 mock）。
- **回归面**：历史上出现过 bug 的区域（从 dev-log 或 git blame 中识别）。
- **安全面**：鉴权检查（未登录用户访问受保护接口）、越权（用户 A 访问用户 B 资源）、注入（SQL 注入、XSS、路径穿越）。
- **UI 关键交互与失败态**：表单校验错误展示、网络请求失败时的 loading/error 状态、空数据状态下的 UI 渲染。

### 单元层级标注 dev-log 覆盖情况

在矩阵的单元列中，对 dev-log 已覆盖的部分标注 `[已覆盖] — 仅补边界/异常`。说明具体还需要补充哪些边界或异常场景，不重写已有的正路径单测。

Author 子 agent 完成后，将 `test-matrix.md` 写入工作目录指定路径，Orchestrator 校验文件存在且非空后进入下一步。

## 范围对抗

Orchestrator 在产矩阵子 agent 完成后，立即委派**独立评审子 agent**（Reviewer 角色，另起全新上下文，不传入 Author 的对话历史）对矩阵进行对抗性审查。

### Reviewer 的任务定义

Reviewer 的唯一职责是**专挑"漏了什么该测的"**：

- 对照 `scope-input-summary.md` 中的实现代码指针，逐类检查矩阵是否遗漏了边界/异常/集成/安全面的测试点。
- 对照常见失效模式（越权访问、事务不一致、异常路径未覆盖、UI 错误态遗漏）审查矩阵是否有系统性盲区。
- 对每一行「超出设计的补充项」列中填写"无"的条目，重点审查对应实现代码，确认是否真的没有补充项。

Reviewer **无写权限**，只输出结构化评审 JSON，不直接修改 `test-matrix.md`。

### 结构化输出要求

Reviewer 必须输出符合 `assets/review-schema.json` 的合法 JSON，保存为 `scope-review-round-1.json`（后续轮次以此类推）。

在测试范围规划阶段，finding 的 `category` 字段**主要为 `coverage-gap`**（覆盖缺口），其次可为 `scope-boundary`（范围边界模糊）或 `prioritization`（优先级存疑）。`coverage-gap` 类 finding 表示：存在一个应测但矩阵未覆盖的测试点，且有实现代码为证（`anchor` 指向代码文件:行）。

典型 `coverage-gap` finding 示例：

```json
{
  "id": "CG-001",
  "severity": "major",
  "category": "coverage-gap",
  "title": "并发注册同邮箱场景未覆盖",
  "detail": "src/api/user.ts:58 存在数据库唯一约束冲突处理逻辑，但矩阵中'用户注册流程'行无并发/竞态测试点，该场景下可能返回 500 而非 409。",
  "anchor": "src/api/user.ts:58",
  "confidence": 0.9,
  "recommendation": "在集成层级补充并发注册同邮箱的测试，验证唯一约束触发时返回 409 且不引发数据库事务泄露。"
}
```

### 迭代处置

Orchestrator 收到 Reviewer 的评审 JSON 后：

1. 解析并校验 JSON 是否符合 `assets/review-schema.json`（优先使用 jsonschema 工具，无则人工冒烟检查关键字段）。
2. 对所有 `coverage-gap` 类 blocker/major finding，委派 Author 子 agent（新实例，传入矩阵当前版本和评审 JSON）对应补全矩阵，写入更新版本。
3. 再次委派 Reviewer 子 agent（新实例）进行下一轮评审，`prior_findings_status` 中追踪上轮 finding 的处置情况。
4. 连续 `K=2` 轮无净进展，或迭代达到 `M=5` 轮上限，停止迭代并上交人类（携带所有轮次的评审 JSON 和矩阵版本快照）。
5. 争议项（Author 认为已覆盖、Reviewer 认为未覆盖的 finding）超过 1 轮持续分歧，立即上交人类裁决，不继续自动迭代。

## 人类检查点①

完成产矩阵与范围对抗后，Orchestrator 向人类报告以下内容，并**等待人类确认**后才能冻结矩阵、进入阶段 1。

### 向人类报告的内容

**1. 矩阵摘要**
- 测试目标清单（行标题列表），共 N 个目标。
- 每个目标在各层级（单元/集成/功能/UI）的适用情况（适用/不适用）。
- 超出设计的补充项数量及分类（边界/异常/并发/安全等）。

**2. 范围对抗结论**
- 共经历 R 轮对抗评审。
- 最终评审 verdict 及 summary（来自最后一轮 `scope-review-round-R.json`）。
- 仍存在争议或未决的 finding（若有）及争议描述，请人类裁决。
- 若因 K/M 触发上交，说明触发原因和当前状态。

**3. 执行环境确认**

向人类说明以下事项，请求确认：

- **隔离分支/worktree**：所有测试代码将在独立 worktree（`git worktree add`）或隔离分支上编写，不直接修改主干。请确认 worktree 路径与分支命名规范。
- **迭代阈值**：本次测试迭代采用 K=2（连续无净进展上限）、M=5（绝对轮数上限）。如有不同要求请现在调整。
- **UI/E2E 执行策略**：若测试矩阵包含 UI 层级的测试目标，将使用宿主的 `preview_*` 工具驱动浏览器执行。若 dev server 无法启动或宿主无浏览器能力，相关用例标记为 `unexecuted` 并在评审 JSON 的 `open_questions` 中记录，不伪造执行结果。请确认此降级策略是否可接受。

**4. 人类裁决项（若有）**
- 列出所有仍有争议的矩阵条目，说明分歧所在，请人类给出最终决策（测还是不测、测到哪个层级）。

### 确认后的操作

人类确认（含对争议项的裁决）后，Orchestrator 执行：

1. 将裁决结果合并入 `test-matrix.md`，写入最终版本。
2. 在 `test-matrix.md` 文件头部写入"矩阵冻结时间戳"和"人类确认签字"（记录人类确认的具体内容）。
3. 建立 worktree（按人类确认的路径和分支名）。
4. 将 `test-matrix.md` 提交至隔离分支，作为后续阶段的唯一范围基准。

冻结后的矩阵不再修改，除非人类在后续阶段发起新的范围调整请求。
