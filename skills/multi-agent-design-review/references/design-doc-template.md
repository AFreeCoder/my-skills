## 0. 已确认需求与约束

> 来自阶段 0「需求理解与澄清」,用户已拍板的结论。这是设计的地基,后续各节不得与此冲突。

- 目标 / 范围 / 非目标(已确认):<...>

## 1. 背景与目标

- 要解决的问题(为什么现在做)。
- 可度量的目标:完成后什么变好、怎么验证。

## 2. 非目标

- 本次明确**不做**的事,划清边界,防止范围蔓延。

## 3. 当前系统现状

- 涉及的真实模块/文件(给路径),现在是怎么工作的。
- 现有约定、数据模型、关键接口。
- ⚠️ 基于真实代码确认,不要假设。这一节失真会带偏整轮评审。

## 4. 方案概览

- 整体思路,一段话讲清。
- 关键设计决策,以及被否的备选方案(为什么选这个、不选那个)。

## 6. 数据结构 / API / 状态流变化

- **数据结构**:新增/变更的字段、类型、约束、默认值、索引、迁移。
- **API**:接口签名(方法、路径、入参、出参、错误码、鉴权)。
- **状态流**:状态机或关键时序,说明状态如何流转、谁触发。

## 7. 兼容性与迁移风险

- 向后兼容:旧数据 / 旧客户端 / 旧接口怎么办。
- 迁移步骤:是否可分步、可灰度、可并存。
- **回滚 / 降级方案**:出问题如何退回,已迁移的数据如何处理。

## 8. 安全、性能、可维护性

- **安全**:鉴权、权限边界、多租户隔离、输入校验、敏感数据。
- **性能**:热路径、复杂度、N+1、缓存、并发与竞态。
- **可维护性 + 可观测性**:日志 / 指标 / 告警,出问题时能否定位与恢复。

## 9. 依赖与前置假设

- 依赖的服务 / 库 / 数据 / 其他团队。
- 本方案成立所基于的假设;若某假设不成立,会发生什么。

## 10. 测试与验证计划

**可验证性原则**:本设计的每个功能点都必须可被验证。下面的矩阵逐功能列出三层验证;**无法验证的功能必须移入第 11 节并说明原因**——那通常是设计本身有缺陷的信号。

### 10.1 功能 × 验证矩阵

| 功能点 | 验收标准(怎样算对) | 单元测试(函数/分支 → 输入/输出) | 功能测试(集成 / 端到端场景) | UI 交互测试(含 UI 才填) | 失效路径验证(超时/空值/并发/部分失败) |
|---|---|---|---|---|---|
| 示例功能 |  |  |  | N/A(纯后端) |  |

- **单元**:覆盖核心函数与分支,给出具体输入 → 期望输出。
- **功能(集成 / 端到端)**:在真实模块协作下验证功能行为,含主路径与边界。
- **UI 交互**:含 UI 的功能必填(点击 / 输入 / 状态切换 / 错误提示 / 加载态 / 空状态等);纯后端 / API 功能标 `N/A`。
- **失效路径**:每个功能都要列出关键失效场景如何被验证。

### 10.2 测试数据 / 环境 / 工具

- 需要的测试数据、夹具(fixtures)、mock、测试环境与工具链。

## 11. 未决问题

- 还没定的设计点、需要用户或团队拍板的取舍。
- **无法验证的功能**(若有):列出并说明为何无法验证、打算怎么办。
