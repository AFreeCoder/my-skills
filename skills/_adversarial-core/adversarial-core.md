# 对抗式迭代内核(Adversarial Iteration Core)

本文档是设计(design)、开发(dev)、测试(test)三个 skill 所共享的**对抗式迭代内核母本**。所有 skill 的副本均为只读,如需修改请在本文件中进行,然后通过 `sync-core.sh` 同步至各副本。文件中凡以占位符 `K`/`M` 出现的阈值,均由各 skill 在自己的配置或提示词中具体化。

---

## 用途与适用

本内核定义了 design / dev / test 三个 skill 所共用的对抗式迭代工作流。其核心思想是:由一个**主笔 agent**(作者角色)产出工件,再由一个**评审 agent**(批评角色)以结构化格式对该工件进行对抗性评审;主笔根据评审结果修订,双方反复迭代,直到满足收敛条件或触发硬上限为止。

这套机制之所以命名为"对抗式",是因为评审 agent 的职责就是找问题——它不是配合主笔"说好话",而是以尽可能严格的眼光审视工件是否满足目标,是否存在遗漏、错误或风险。主笔与评审之间的摩擦是刻意制造的,目的是在交付给人类之前尽量暴露缺陷。

**副本只读原则:**各 skill 目录下的 `adversarial-core.md` 均为本文件的同步副本,不得直接修改。如发现问题或需要演进,应修改本母本,再执行 `sync-core.sh` 统一分发。这样可确保三个 skill 始终使用同一份规则,避免规则漂移。

**阈值与 category 的定制点:**连续无净进展轮数上限(`K`)、绝对迭代轮数上限(`M`)、以及评审 finding 的 `category` 枚举值,均与具体领域强相关,本内核不预设固定值。各 skill 在自己的评审提示词(review prompt)或配置文件中填入适合自身场景的具体值,并附上领域示例。

---

## 评审分级(severity)

每条 finding 必须标注一个 severity 等级。等级决定了该 finding 是否构成迭代阻断因素,也决定了收敛判定的计数方式。以下是三级的**通用定义骨架**,各 skill 在自己的评审提示词中可在此基础上补充领域特定的示例与判定细节。

**blocker(阻断)**
不解决不能推进。以下任一情形均属 blocker:正确性错误(程序会产出错误结果)、数据错误或数据丢失风险、安全漏洞、与现状(已有系统/接口/数据格式)不兼容且无迁移路径、核心假设不成立(工件建立在错误前提之上)、核心目标无法达成(工件根本不能完成既定目标)、核心目标完全无法验证(没有任何途径可以确认目标是否实现)。只要存在一条未解决的 blocker,评审结论就不能为 `approve`。

**major(重要)**
严重但不绝对阻断。以下情形通常属于 major:重要的失效路径未覆盖(边界条件、异常分支被忽略)、关键测试缺失(测试覆盖不足以在回归时发现已知风险)、性能或可维护性存在实质性隐患(不是主观偏好,而是客观上会导致系统退化或难以演进)、缺少回滚方案(变更一旦出问题无法安全撤回)。major 不直接阻止工件前进,但在收敛计数中占有与 blocker 同等的地位——连续多轮 major 无净进展同样触发上交人类。

**minor(改进项)**
不阻塞迭代,也不参与收敛计数。minor 是"更好但不是必须"的改进意见:代码风格、文档补充、命名优化、非关键路径的轻微低效等。minor 不得单独阻止工件推进,评审者在产出 minor finding 时应说明"这是改进建议,不是必须修复"。主笔可选择性采纳,未采纳的 minor 进入「已知债务」列表备案。

**关于 category 字段:**`category` 是对 finding 领域属性的进一步分类(例如 dev skill 中可能有 `logic`、`security`、`test-coverage`、`performance` 等)。具体 `category` 取值与领域示例由各 skill 在自己的评审提示词里补充。本内核不强制枚举,以保持通用性。

## 结构化评审输出

评审 agent 的每次评审必须输出符合 `assets/review-schema.json`(该路径相对 skill 根目录;母本同步后副本即位于各 skill 的 `assets/review-schema.json`)的合法 JSON,不接受自由文本或非 JSON 格式的评审结论。结构化格式的存在意义在于:使主笔 agent 和宿主 skill 能够机械地解析评审结果、追踪 prior finding 状态、进行收敛判定,而无需依赖语义理解。

评审输出的顶层字段:`verdict`(approve / needs-revision)、`summary`(一句 ship / no-ship 式总评)、`findings`、`prior_findings_status`、`open_questions`。

**`anchor` 字段是评审有效性的最低门槛。**每条 finding 必须携带 `anchor`,用于精确定位被评审的目标。根据领域不同,`anchor` 的形式可以是:文件路径+行号(`src/api/user.ts:42`)、接口/方法名(`UserService.createUser`)、数据流节点(`input→validate→persist`)、或测试用例名(`test: 用户注册成功路径`)。**没有 `anchor` 的 finding 视为无效评审**,主笔有权拒绝响应,宿主 skill 有权将其排除在收敛计数之外。这条规则的目的是防止评审 agent 产出空洞的、无法定位的泛泛批评。

**`confidence` 字段要求如实填写。**`confidence` 是 0 到 1 之间的浮点数,表示评审者对该 finding 成立的把握程度。当 finding 依赖推断(例如评审者无法直接看到某段逻辑,只能从上下文推测)时,`confidence` 应相应降低,不得虚报高置信度。宿主 skill 可以根据 `confidence` 决定是否要求评审者提供更多证据再决策。

**`prior_findings_status` 字段追踪上一轮 finding 的处置情况。**从第二轮起,每次评审必须对上一轮的所有 blocker 和 major finding 逐条给出状态:`resolved`(已解决,附证据)、`partially_resolved`(部分解决,说明剩余问题)或 `unresolved`(未解决,说明原因)。这是净进展判定的数据来源。

## 终止规则机制(收敛判定 + 硬上限)

迭代不能无限进行。终止规则机制定义了何时认为迭代已经收敛(可以结束)、何时应当停下来上交人类(无法自动收敛)。**具体阈值 `K`(无净进展轮数上限)和 `M`(绝对轮数上限)由各 skill 自行配置**,本内核只定义通用机制。

**净进展的定义:**一轮迭代相较于上一轮存在净进展,当且仅当以下至少一项成立:在本轮的 `prior_findings_status` 中,至少一条上轮的 blocker 或 major 被标记为 `resolved`;或者,本轮评审中 blocker + major 的未解决总数严格小于上轮。仅仅"新增了 minor"或"措辞改善"不构成净进展。**打转判定**:若本轮新增的 blocker/major 数量 ≥ 本轮解决的 blocker/major 数量,则认为迭代在原地打转,视为无净进展。

**软规则——停止并上交人类:**出现以下任一情形时,停止当前迭代单元,将完整状态(所有轮次的评审 JSON、当前工件、分歧摘要)上交人类决策:连续 `K` 轮无净进展(说明迭代卡死,自动循环无法突破);或主笔与评审就某条 blocker/major 存在持续分歧(主笔认为已解决,评审认为未解决,且连续出现超过 1 轮)。软规则触发时不得静默丢弃问题,必须明确报告触发原因。

**硬上限——强制停止:**无论软规则是否触发,迭代轮数达到 `M` 轮时必须强制停止,将当前状态上交人类。硬上限是防止 agent 在异常情况下无限循环的最后一道保险。到达硬上限不代表工件不可用,只代表自动迭代能力已耗尽,需要人类介入判断。

**正常终止条件:**若某轮评审的 `verdict` 为 `approve`,且当轮 `prior_findings_status` 中所有上轮 blocker/major 均为 `resolved`,且当轮 findings 中不含新的 blocker/major,则正常终止迭代,将工件标记为"已通过对抗评审"。

## 反作弊纪律

对抗式迭代内核的有效性依赖于 agent 严格遵守以下纪律。任何违反均视为严重的流程错误,宿主 skill 应立即停止迭代并上报。

① **禁止将缺失/失败/不合 schema 的评审当作通过处理。**若评审 agent 未产出输出、产出的 JSON 无法解析、或 JSON 不符合 `review-schema.json` 的校验,宿主 skill 必须视为评审失败。不得以"评审静默=没有问题=通过"为由推进迭代。

② **禁止伪造任何命令执行结果、参数、端点、产物或评审内容。**主笔和评审 agent 均不得编造命令的输出、假设某个接口存在并以此为据、或凭空生成一份"看起来合理"的评审 JSON。所有声称"已执行"的操作必须有真实的退出码和产物为证。

③ **任一外部调用失败,必须如实处理,不得当作成功。**若调用 `codex exec`、`claude -p` 或任何外部 CLI 时收到非 0 退出码、stderr 有错误输出,或产物文件不存在/为空,则该调用失败。失败后至多重试一次(见看门狗章节),仍失败则停止迭代并上报,绝不能将失败的调用结果当作"通过"继续走流程。

④ **主笔不能单方面把 blocker/major 降级。**如果评审将某条 finding 标为 blocker 或 major,主笔在回复中可以提出异议,但不得自行将其降为 minor 或从下一轮的 `prior_findings_status` 中移除。如果主笔与评审就某条 finding 的 severity 存在分歧,必须上交人类裁决。

⑤ **无法验证的目标移入「未决问题」并说明原因。**若某个验收条件在当前上下文中无法被客观验证(例如需要真实用户数据、需要访问无法访问的外部系统),主笔不得声称"已满足",而应将其移入评审 JSON 的 `open_questions` 字段,说明无法验证的原因和缺少的条件。

## 看门狗 / 存活监控

调用外部 CLI(如 `codex exec` 或 `claude -p`)时,**必须将其包裹在宿主原生 subagent(Agent tool)中,以前台同步方式运行,不允许主 agent 直接裸跑**。这是因为:长时间运行的子进程在某些宿主环境中可能被自动后台化,其子进程可能被静默终止,而主 agent 无法感知这一情况,会一直等待或错误地将超时等同于成功。通过 subagent 包裹并同步等待,可以确保结果明确可得。

**退出码语义:**宿主 skill 必须检查外部 CLI 的退出码并按以下规则判定:
- `0`:调用成功,继续检查产物。
- `1`–`2`:CLI 自身报错(通常是参数错误或内部异常),检查 stderr 获取错误信息。
- `≥ 128`:被操作系统信号终止,`137` = SIGKILL(通常是 OOM 或超时强杀),`143` = SIGTERM(优雅终止请求)。

**成功判定:**退出码为 `0` **且**预期产物文件存在且非空。仅有退出码 0 而无产物,或有产物但为空/损坏,均视为失败。

**死亡判定:**产物文件缺失,或退出码 ≥ 128,或 stderr 报告致命错误,均视为调用死亡。

**重试策略:**任何失败(包括死亡)至多重试**一次**。重试前应记录失败的退出码和 stderr。若重试仍失败,则立即停止迭代,将失败详情和当前状态上交人类,不得进一步重试或绕过。

## 文件驱动协作

对抗式迭代内核采用**文件作为唯一的跨调用状态载体**。主笔 agent、评审 agent、以及宿主 skill 之间的所有协作信息——当前工件、历史评审 JSON、轮次计数、净进展计数——均须落地为文件,不依赖 agent 的会话内记忆或变量传递。

**理由:**每次通过 Agent tool 调用子 agent 时,子 agent 都在全新的上下文中启动,不携带任何对话历史。如果状态只存在于主 agent 的上下文中而未写入文件,子 agent 就无法获取必要信息,导致重复工作或状态丢失。

**操作规范:**
- 宿主 skill 在每次启动子 agent(主笔或评审)时,必须在 prompt 中**显式传入**所需文件的绝对路径。不得用"上次的输出"等模糊引用。
- 子 agent 完成后,宿主 skill 负责将其输出写入指定文件,供下一轮子 agent 读取。
- 每轮评审的 JSON 输出应按轮次编号保存(如 `review-round-1.json`、`review-round-2.json`),便于追溯和上交人类时提供完整历史。
- 工件本身每轮也应有版本快照或明确的"当前版本"文件路径,避免主笔 agent 因找不到上一轮修订后的工件而从头重写。

## 输出校验

每轮评审产出后,宿主 skill 必须在将其用于收敛判定之前执行输出校验。校验分为两个层次:

**层次一:schema 校验(优先)**
若运行环境中存在 `jsonschema`(Python)或等效的 JSON Schema 校验工具,必须使用它对评审输出执行完整校验,对照 `assets/review-schema.json`。校验失败即视为评审无效,触发反作弊纪律第①条。

**层次二:关键字段冒烟校验(回退)**
若无 JSON Schema 工具可用,至少执行以下冒烟检查,任一失败均视为评审无效:
- `verdict` 字段存在,且值为 `"approve"` 或 `"needs-revision"` 之一。
- `findings`、`prior_findings_status`、`open_questions` 均为列表类型(即使为空列表也可接受)。
- `summary` 字段存在且为非空字符串。
- `findings` 中每条 finding 的 `severity` 值为 `"blocker"`、`"major"` 或 `"minor"` 之一,`confidence` 为 0 到 1 之间的浮点数,且 `id`、`category`、`title`、`detail`、`anchor`、`recommendation` 均为非空字符串。

**强制约束(任一层次均适用):**若上一轮存在 blocker 或 major 的 finding,且本轮的 `prior_findings_status` 中该 finding 的状态为非 `resolved`,但本轮 `verdict` 却为 `approve`——则**无论 schema 校验是否通过,该评审结论违反终止规则,视为无效**。宿主 skill 必须拒绝该 `approve` 判定,将情况记录为"评审逻辑矛盾",并触发软规则上交人类,因为这表明评审 agent 出现了自相矛盾的行为。
